# Review meaning and the reader's route

Assess the requested scope against the project's current terminology, decisions and sources. Treat historical quotations and machine identifiers as evidence, not automatic editing targets. Separate a conflicting domain meaning from a stylistic preference.

## Four outcomes

| Outcome | Check |
| --- | --- |
| Consistency | Shared concepts retain their meanings across artefacts and audiences; aliases and context translations are explicit |
| Accessibility | Readers can find purpose, main point, consequences and detailed sources without guessing implementation vocabulary |
| Readability | Terms and paragraphs form a connected explanation at the required depth |
| Repeatability | Another author can use the same references and pattern to preserve meaning and navigation |

Trace consequential claims to their source and scope. Check that a summary preserves constraints. Inspect first-use definitions, heading hierarchy, link text and the textual route through essential visuals. Identify unnecessary abstraction with an actual replacement example, rather than labelling the document “dense”.

## Follow one meaning across artefacts

For a review spanning several artefacts, choose the consequential concept and follow its current definition and source into the task, decision, documentation and audience copy. Check the conditions each artefact retains, the state it describes and the next action it permits. A label can change for its audience while its meaning stays fixed. Record a conflict against the source instead of polishing the conflict into fluent prose.

Invented example: the project defines **reviewed** as “all required checks completed”, while eligibility is a separate decision. “Your report is approved” changes that meaning. “All checks are complete. View the eligibility decision” preserves the distinction if that decision exists. Keep the exact internal value in contracts and translate its consequence where users need it.

## Make consequential edits inspectable

When an annotated revision is requested, or a substantial edit needs explanation, use a compact note or table with these fields: original wording, revised wording, reason, retained facts and conditions, and governing source or open question. Show representative or consequential edits rather than an exhaustive diff by default. Plain text is enough; a visual comparison is optional.

For example, changing “Exports are available” to “Workspace members can export the last 30 days as CSV” is justified only if those conditions are in the source. Name that source in the note. If the conditions are unknown, keep the supported wording and record the question rather than inventing specificity. Revision notes explain authorised work; they do not add a new approval gate.

## Use concrete patterns for a detailed edit

For sentence-level or cross-artefact editing, consult the relevant [editorial patterns](editorial-patterns.md). The reference provides stable identifiers, source facts, revisions and exceptions for changed meanings, lost conditions, unsupported claims and other consequential problems. Read only the patterns relevant to the finding; a small correction does not require the full catalogue. Use the identifier to make a finding easy to locate, not to assign an AI-authorship or writing-quality score.

## Findings that enable revision

For each material finding, give the location, observed wording, effect on understanding and smallest useful correction. Prioritise changed meaning and false claims before vocabulary drift, weak navigation and cosmetic preferences. If no material defect is found, say so without inventing findings.

When a source is missing, state the exact unresolved claim and how to establish it. Do not turn an unrun check into a blanket rejection. Preserve genuine blockers and the independent work that can continue.

Use configured linters for specific signals; assess context before applying a suggestion. Reading-age and sentence-length scores do not establish comprehension. Keep deterministic findings, independent agent judgement and actual human reading observations separate.

When revisions are authorised, change the requested artefact and verify retained facts. For a review-only request, provide actionable findings without silently modifying unrelated material or historical decisions.

## Sources and local adaptation

[Microsoft's plain-word guidance](https://learn.microsoft.com/en-us/style-guide/word-choice/use-simple-words-concise-sentences), [Google's jargon guidance](https://developers.google.com/style/jargon) and the [ISO 24495-1 public abstract](https://www.iso.org/standard/78907.html) inform reader-focused checks. The repository's four outcomes express Jason's priorities; they are not a quoted ISO checklist. Meaning and reader navigation require contextual review alongside selected automated signals.

The compact revision notes were informed by the [Hamel Plain Writing fork's inspectable revision workflow](https://github.com/hamelsmu/plain-writing-skill/blob/295afb568bccbd816912816312ef89a195f1752f/SKILL.md). The format and examples here are local; no HTML template is copied. [Humanizer v3.1.0](https://github.com/blader/humanizer/blob/0ef9fe5bc3572734fd3ae6c448fe00a30cd5dcf0/SKILL.md) supplies useful examples of explicit factual checks and contextual exceptions. These ideas support editing within the project's established meanings, not an AI-authorship score.
