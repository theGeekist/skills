# What the collection contributes

Geekist Skills connects project meanings, source authority and evidence state across the documents and interfaces people use to deliver a change. Established writing principles and existing editorial skills supply important foundations. The implementation brings those principles into purpose-specific project workflows.

## Separate foundations from local implementation

| Concern | Foundation or related work | Inspectable Geekist implementation |
| --- | --- | --- |
| Clear expression | Plain-language guides and competing editorial skills | One [shared baseline](../../standards/baseline.md), generated into every independently installable skill |
| Project meaning | Bounded contexts, SKOS labels and Good Docs terminology | [Discovery and maintenance workflow](../../skills/establish-project-language/SKILL.md), explicit JSON records, sources, context and aliases |

| Meaning across artefacts | Terminology and editorial review | [Project-language review](../../skills/review-project-language/SKILL.md) traces accepted terms and source constraints through connected artefacts rather than judging sentence style alone |
| Architecture | Jason's existing backend and frontend rules | Independently packaged playbooks with protected rule authority; editorial improvements preserve the original conditions and exceptions |
| Inspectable revisions | Related review-output practices, including the Plain Writing fork | Optional compact revision records show consequential edits, reasons and retained constraints without requiring HTML output for every edit |

This is a description of the implementation and its scope, not a claim to be the first project with any individual practice. The [competitive review](competing-writing-skills.md) identifies real overlaps and useful alternatives. The contribution is inspectable in the connected workflow below and the source-linked implementations above.

## Follow one meaning into several artefacts

Consider an invented workshop booking system. Its accepted definition says an eligible attendee meets the admission conditions; eligibility does not mean a booking has been confirmed.

A project-language review should detect a task that implements eligibility correctly but a dashboard that calls every eligible attendee “confirmed”. A clear sentence alone would not repair that discrepancy. The reviewer follows the accepted definition, identifies the changed meaning and proposes wording that preserves the distinction in both places. Marketing can explain the benefit without promising automatic confirmation.

If the eligibility check has not been measured under load, that missing measurement becomes an explicit validation action and a condition on performance claims. Authorised implementation can continue unless an actual dependent step is blocked. The editorial example does not create booking or admission rules for a real project.

This connects three responsibilities: maintain the meaning, fit the artefact to its reader and preserve the relationship between implementation and evidence. The [all-skill walkthrough](skill-walkthrough.md) shows a longer route, and each [skill overview](../skills/) exposes its own purpose and example.

## Adopt competitor lessons without flattening the collection

The current improvements add visible examples, optional revision inspection, direct overview pages and generated presentation metadata. They retain existing source attribution and the original architecture model. Competing style preferences are not imported as universal bans on punctuation, metaphors, humour or uncertainty.

The collection remains eleven focused entry points. A request can select the relevant skill directly; the compatibility router is explicit and the research catalogue is optional context. Neither installation nor generated client metadata proves native activation.

## Evidence for the change

Automated checks cover source/reference drift, presentation consistency, installation routes and package structure. Task trials exercise the language guidance on bounded examples. Separate records identify agent assessment, executed checks and observations still needed from human readers or native clients. These checks do not establish superiority to competing writing skills or improved search rankings.
