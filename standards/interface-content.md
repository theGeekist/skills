# Interface language follows the user's situation

Use the current domain definitions and real product states. Preserve meaning when mapping internal values to public wording. Labels, alerts, dashboard descriptions and recovery actions should help the user understand what happened and what they can do next.

## Choose the pattern

| Situation | Useful content |
| --- | --- |
| Action | Concrete verb and object; consequences where necessary |
| Progress | Actual work completed, meaningful movement, supporting event and next milestone |
| Error | What happened, practical effect and available recovery |
| Empty state | Why the view is empty and a useful next action |
| Permission boundary | The unavailable action and legitimate route to access |
| Metric | Meaning, unit, period, relevant comparison and deeper definition |

For dashboards, separate result, confidence in the result, check coverage and execution progress when the domain does. A rising progress bar does not establish a stronger assessment. Derive changes from actual events and avoid double-counting work. Label invented examples clearly during design.

Celebrate observable progress where appropriate. Keep unresolved checks connected to the work still moving. A raw “unqualified” state may be honest internally while an audience explanation can describe what has been completed and what remains. Preserve consequential limitations in an accessible detail route.

## Explain movement without changing the result

Invented state: one of three checks has finished, and eligibility has not been decided. “33% qualified” changes progress into an assessment. “1 of 3 checks complete” reports the event; add the next check or available action when known. Keep the eligibility result separate.

The best label is sometimes the established specialist term, especially in an expert tool. Retain it with a useful explanation rather than forcing an everyday synonym that merges distinct states.

## Accessibility and coherence

Use consistent action names across buttons, confirmations and help. Explain specialised labels at the point of use. Make essential information available in text; colour, motion and a chart alone cannot carry the result. Prefer meaningful link text and a clear reading order.

Keep microcopy short enough for the context without removing the condition that changes a user's choice. Use progressive disclosure for calculation detail and diagnostics. A tooltip should not be the sole route to a critical warning or definition.

Validate proposed wording against the states that actually exist, including interruption, partial completion, stale data and recovery. If a state is missing from the contract, record a proposal rather than inventing product behaviour.

## Sources and local adaptation

[Atlassian's voice and tone guidance](https://atlassian.design/foundations/content/voice-tone/) informs wording that responds to the user's situation. The state distinctions, progress-event requirements and domain-preserving labels here are local rules. Atlassian's public UI guidance is not being presented as its internal marketing framework or as validation of a product's state model.
